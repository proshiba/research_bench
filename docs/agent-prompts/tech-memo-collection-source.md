# 依頼: IOC の「収集元」が常にその日の 1 本目の記事を指している

## 症状

`search.json` の IOC エンティティが持つ `refs` の `収集元` が、**その IOC が実際に
載っていた記事ではなく、常にその日の 1 本目の記事 (`#0`) を指しています。**

ポータルのワークベンチで IOC を展開すると、まったく無関係な記事がぶら下がります。
利用者から次の形で報告がありました。

```
入力:       haochisadnka.cc          （ValleyRAT の C2 ドメイン）
引かれたもの: Apple、偽の App Store 暗号資産ウォレットアプリによる
             180 万ドル相当の Bitcoin 窃取で提訴
```

**調査の起点として使えないため、実害が出ています。**

## 何が起きているか（実データで確認）

`収集元` の辺は **6,106 件すべてが `#0` を指しています**。

```
収集元 の辺: 6106
記事番号の分布: [ [ '0', 6106 ] ]
記事: 7329 件 / 944 日 / 1 日あたり中央値 7 本・最大 21 本
```

1 日に平均 7 本の記事があるのに、参照は必ず `#0` です。参照切れにはならないので、
既存の検査はすべて通ってしまいます。

### 実例（2026-07-28）

その日の記事は 6 本あります。

| id | 見出し |
| --- | --- |
| `article:20260728#0` | Apple、偽の App Store 暗号資産ウォレットアプリによる… |
| `article:20260728#1` | Coca-Cola、Fairlife へのランサムウェア攻撃で… |
| `article:20260728#2` | ShinyHunters 恐喝グループ、Ernst & Young の… |
| **`article:20260728#3`** | **SparkKitty マルウェア：モバイル利用者を狙う新たな脅威** |
| `article:20260728#4` | vBulletin のランタイムテンプレート「runMaths」に… |
| `article:20260728#5` | サンドボックスを再び突破：n8n の CVE-2026-27577 修正を回避 |

この日に収集された IOC 37 件は**すべて `マルウェア: SparkKitty`** で、`#3` の記事の
ものです。それでも 37 件全部が `収集元: article:20260728#0` になっています。

### 影響の規模

`マルウェア` 属性を持ち、その日に記事が 2 本以上ある IOC 5,011 件で照合しました。

| | 件数 |
| --- | --- |
| 指し先（`#0`）の見出しにマルウェア名がある | 396 |
| **同じ日の別の記事の見出しにマルウェア名がある（＝誤り）** | **1,741** |
| どの見出しにも名前がない（見出しに出ないこともあるので判定不能） | 2,874 |

396 件は**偶然 `#0` が正解だった**ものです。つまり `収集元` は基本的に当たっていません。

## お願いしたいこと

**IOC を起こした記事の id を `収集元` に入れてください。** 生成時にはどの記事の
本文から抽出したか分かっているはずなので、その id をそのまま使う形になると思います。

現状は「その日の記事の先頭」を既定値として入れているように見えます。

### 直せない場合

**`収集元` の ref を出さないでください。** 誤った参照は、参照が無いことより悪いです。
記事との対応は、`malware` / `actor` 実体が持つ `関連イベント`（→ `report`）から
別途辿れます。

## ポータル側の暫定対応

直るまでのあいだ、ポータルは**この関係の辺を作りません**。

「id が `<家族>#<番号>` の形をしていて、同じ家族に兄弟が複数いるのに参照が常に同じ番号を
指している関係」を読み込み時に検出し、除外します（`assets/js/store.js` の
`detectBrokenRefs`）。除外したことは画面に出します（黙って減らすと「関連が無い」と
読めてしまい、索引が壊れていることに気づけないため）。

`収集元` が正しくなれば検出条件から外れ、自動的に辺が復活します。**この依頼の完了後に
ポータル側で何か作業する必要はありません。**

## 検査

同じ検出を共通チェッカー `docs/validate-index.py` に入れました。公開前に流せます。

```
$ python3 docs/validate-index.py <meta.json> <search.json>
  エラー: rel `収集元` の参照先 6,106 件がすべて `#0` を指しています。
          同じ家族に兄弟が複数いるので、参照先が選ばれていません
          （生成側で既定値のまま出ている疑い）。ポータルはこの関係の辺を作りません
```

`言及記事`（14 種）と `関連イベント`（19 種）は正常に散っているので、何も出ません。
直った `収集元` も同様に通るはずです。

部分的に既定値が残っている場合も拾えるようにしてあります（`#0` の件数が兄弟数から
期待される件数の 3 倍を超えたら警告）。
