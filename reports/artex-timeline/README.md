# ARTEX_TIMELINE

利用者が特定した攻撃クラスタについて、AbuseIPDB 上の通報を時系列に並べたもの。

## 1 つのクラスタです（2026-11-06 に訂正）

**元は ARTEX と sub2api を別のクラスタとして扱っていた。これは誤りだった。**
利用者の指摘により、`38.11.173/221` 側にも sub2api があり、**全 255 IP に同じ
リチャージ URL (`198.200.59.85`) がセットされている**と分かった。
つまり 1 つのクラスタで、そのうち 250 IP では ARTEX も起動している。

**役割はクラスタではなく IP に付ける印にした。**

| 役割 | 対象 | 利用者の観測 |
| --- | --- | --- |
| `sub2api` `artex` | `38.11.173.0/25` と `38.11.221.0/25` の `.1`〜`.125`（250 IP） | ARTEX も起動している |
| `sub2api` `recharge_host` | `198.200.59.85`（1 IP） | リチャージ URL のホスト自身。自分を指している |
| `sub2api` | `198.200.59.86`〜`.89`（4 IP） | ARTEX は観測されていない |

別クラスタとして持っていたせいで「2 つのクラスタは繋がるか」という**本来不要な
問いが立ち、経路表（AS54600）を根拠に据えていた**。繋がりの根拠は利用者の観測
（同じリチャージ URL）であって、経路表はそれとは別の裏づけに過ぎない。

```sh
ABUSEIPDB_API_KEY=k node fetch.mjs   # **ここだけが外に出る**（255 件）
node build.mjs      # 写しから CSV と summary.json。API は呼ばない
node report.mjs     # CSV から日本語レポート
node validate.mjs   # 成果物を読み直して検査（89 項目）

# 再調査するときは写しの鮮度に注意（下記）
ABUSEIPDB_API_KEY=k node fetch.mjs --refresh
```

## 能動調査はしない

**対象 IP への接続・走査・認証試行は一切行わない。** ポートスキャンもせず、HTTP も
叩かず、ping も打たない。AbuseIPDB の公開情報と、手元の索引だけを見る。

## 結論（2026-11-06 時点）

| 問い | 答え |
| --- | --- |
| 通報されるようになったか | **はい。255 IP のうち 10-30 は 44、11-06 は 65** |
| それは複数の観測者が攻撃を見たことか | **部分的にそうなった。**11-06 に `artex` の 8 IP へ初めてフィード以外の通報（通報者は 1 人） |
| 何として通報されたか | フィードぶんは **Exploited Host（20）だけ**。11-06 に付いたのは **Web App Attack（21）** |
| リチャージ URL のホストは | **`198.200.59.85` が最初（09-30）で最多**（通報 3 件 / 通報者 3 人）。隣の `.86`〜`.89` は**一度も通報されていない**（ただし 4 IP では差と呼べない） |
| 日本からの通報 | **0 件** |

## 一番間違えやすいところ

### 1. 通報の件数ではなく通報者の数で見る

「複数の IP が攻撃元として報告されている」は、**通報の件数ではなく通報者の数**で
見ないと意味を取り違える。11-06 時点で通報 68 件のうち **58 件が単一の通報者**（BR）で、
日付以外は同じ定型文、カテゴリも Exploited Host だけ。**これは脅威情報フィードの
一括登録で、被害者が「攻撃された」と通報したものではない。**

### 2. `reportedAt` は観測日、`lastReportedAt` は投稿日（2026-11-06 に実測）

**この 2 つを同じ「通報日時」として扱うと時系列が壊れる。**

| フィールド | 意味 | 活動日として読めるか |
| --- | --- | --- |
| `reportedAt` | 通報者が申告した**観測**時刻。さかのぼれる | **読める** |
| `lastReportedAt` | AbuseIPDB が最後に通報を**受け取った**時刻 | **読めない** |

実測した根拠:

- フィードの本文 `... Last observed <日付> UTC.` の日付が `reportedAt` の日付と
  **58/58 件一致**。つまり `reportedAt` は通報者側の観測日
- `lastReportedAt` は 57/65 件で `reports[]` の最新より**後ろ**にあり、前になった例は 0 件
- さかのぼり日数は中央 **1.04 日**・最大 **7.32 日**（通報 1 件の 63 IP で測定）
- 投稿時刻は 56 件中 40 件が 01 時台（UTC）に固まる。観測時刻は 00/04/16/18 時に散る。
  **別の時計で動いている**

ここから 2 つ出てくる。

1. **`lastReportedAt` を活動日として図に載せてはいけない。**投稿日なので、
   その日に攻撃があったことを意味しない
2. **過去の日付の集計は確定しない。**同じ IP を後日引き直すと、**過去の日付の通報が増える**

実際に起きた。10-30 の取得では通報 0 件だった 14 IP が、11-06 には「10-27 観測」の
通報を持っていた。投稿日は 11-02〜11-04。**10-30 の取得は間違っていない。**
当時まだ投稿されていなかっただけ。validate がこの関係（古い日付で増えた通報の投稿日が
前回の取得以降であること）を毎回確かめる。

### 3. フィードと被害者側の観測を分ける印

件数と定型文だけでは両者が同じ形に見える。`IN-R04` も 8 件を 10 秒間に同じ本文で
出している。分けるのは次の 2 つ。

| | フィード（`BR-R01`） | 被害者側（`IN-R04`） |
| --- | --- | --- |
| さかのぼり最大 | **7.32 日** | **0.00 日** |
| 対象（255 IP の） | 22.7% | 3.1% |
| カテゴリ | Exploited Host（20） | Web App Attack（21） |

**フィードは手元の台帳をまとめて流すので観測日をさかのぼる。被害者側の検知器は
見たその場で出すのでずれが 0 になる。**

### 4. カテゴリ 20（Exploited Host）は攻撃手法ではない

「この送信元自体が侵害されている可能性」を示す補助情報。踏み台にされた正規ホストなら、
送信元の持ち主も被害者である。「この IP が攻撃してきた」とは違う。
**カテゴリ 21（Web App Attack）は攻撃手法そのもの**で、意味が違う。

### 5. 「フィードだから割り引く」はどこまで言えるか

この母集団で 2×2 を数えると、フィード掲載は被害者側の通報を**予測しなかった**。

| | IP | フィード以外の通報がある | 割合 |
| --- | --- | --- | --- |
| フィードに載っている | 58 | 2 | 3.4% |
| 載っていない | 197 | 7 | 3.6% |

**ただし差を論じるには足りない**（正例が 9 件しかなく、数件の上下で逆転する）。
`underpowered: true` を summary に出している。言えるのは、フィード掲載は
「誰かが悪性と判断した」情報であって無価値ではないが、**「被害者が攻撃を観測した」
とは別の情報**だということ。

### 6. 定型文を数えるときは日付を畳む

最初の版は本文をそのまま比べたため、`Last observed 2026-10-17` と `2026-10-24` が
別の本文に見え、**44 件 1 人の一括登録を取り逃がした**。日付と数字を `<date>` `<n>`
に畳んでから数える。

## 比較の基準は `snapshots/` の CSV

`.cache/` は git 管理外で容器も使い捨てなので、**前回の写しは次の調査では無い**。
実際 11-06 の容器には 10-14 の写し（`config.json` の `BASELINE`）が無く、基準が
消えていた。そこで前回の成果 CSV を `snapshots/<日付>_by_ip.csv` と
`snapshots/<日付>_events.csv` に残し、そこを基準にする。写しは消えても CSV は残る。

**今回ぶんのスナップショットを「前回」に選ばないこと。** 選ぶと自分自身と比べて
差分が全部 0 になる。取得日より前のものだけを候補にしており、validate がこれを
確かめる（2 回実行の md5 比較で一度踏んだ）。

## 写しの鮮度（2026-11-06 に直した）

以前は `!fs.existsSync(slot(ip))` だけで引くかどうかを決めていた。つまり
**一度写しを取ったら何日経っても二度と引き直さない**。`.cache/` が消える環境では
実害が出ていなかったが、写しが残った容器で再調査を回すと**黙って前回の写しを
読み直し、「変化なし」という嘘の結論が出る**。既定 20 時間で古いと見なし、
`--max-age-hours` と `--refresh` を付けた。`fetch_meta.json` に
`fetched_now` と `reused_copies` を分けて残す。

## 検査が古い結論を固定していた（2026-11-06）

元の validate はこう書いていた。

```js
check(artexRids.size === 1, "ARTEX の通報はすべて単一の通報者")
check(indep.every((e) => e.cluster === "sub2api"), "ARTEX には独立した通報が無い")
```

11-06 にこの 2 つが落ちた。**落ちたのが正しい。** ARTEX に初めてフィード以外の通報が
付いたから。検査が「10-30 時点の世界」を正しさとして焼き込んでいた。

**事実が変わったら落ちるべき検査と、壊れたら落ちるべき検査は別物。** 前者は
数え直して summary と突き合わせる形に直し、後者（鍵が漏れていない、`reporterId` が
出ていない、並び順、合計の一致）はそのまま残した。

## 経路表（根拠は 10-14 のもの。繋がりはこれに依らない）

**クラスタの繋がりの根拠は利用者の観測（全 255 IP に同じリチャージ URL）である。**
経路表はそれとは別の裏づけに過ぎない。

AbuseIPDB の ISP の答えは割れる（`artex` 側は Cogent、`198.200.59.x` は PEG TECH）。
経路表ではどちらも同じ AS だったが、**11-06 には再確認していない**
（手元の索引に 3 帯とも 0 件のため）。

```
38.11.173.1    → 38.11.160.0/19   AS54600 PEG TECH INC (US)
38.11.221.1    → 38.11.192.0/19   AS54600 PEG TECH INC (US)
198.200.59.85  → 198.200.32.0/19  AS54600 PEG TECH INC (US)
```

`artex` 側の ISP が Cogent と出るのは食い違いではなく、ARIN RDAP に下位割当（SWIP）の
登録が無いため（2026-10-14 に確認）。

`198.200.59.85`〜`.89` の rDNS は 5 件すべて `visiblooths.net` の下で、`murves`
`moxley` `dyres` `sozel` `olarm` という 5 文字の無意味な名前（11-06 も同じ）。
一方 `artex` の 250 件はすべて rDNS が空。**rDNS の出方が役割で割れている。**

## 言えないこと

- **ARTEX や sub2api が動いているかは確認していない。** 能動調査をしていないので、
  待ち受けているサービスも見ていない。利用者から渡された前提のまま
- **「攻撃に使われた時期」は確定しない。** さかのぼり投稿があるので、今日の集計は
  明日増える。`reports[]` は観測の下限しか示さない
- **フィード以外の通報者は 3 人しか居ない。** `artex` の 250 IP については 1 人。
  「複数の被害者が独立に観測した」とまでは言えない
- **`IN-R04` がどういう通報者かは分からない。** 全体での通報傾向を調べるには
  `reporterId` を蓄積する必要があり、方針で保存していない。言えるのは
  **この 255 IP の中での選択性（3.1%）**だけ
- **通報が無いことは無害の証明ではない。** 立てたばかりの基盤や、通報しない被害者しか
  居ない基盤は同じ見た目になる
- AbuseIPDB のカテゴリと観測時刻はレポーターの自己申告
- IP の所在地・ISP・AS は、運用者の国籍や所属を示さない
- 母集団は渡された 255 IP だけ。同じ AS の他の帯は見ていない
- **`.86`〜`.89` に通報が無いことに意味があるとは言えない。** 4 IP では差と呼べる数にならない

## 残していないもの

- `reporterId` の値は保存しない（`BR-R01` のような識別子に置換し、同じ人かどうかだけ分かる）
- 通報コメントの原文は保存せず、無害化して短く切ったものと SHA-256 だけ残す
- API キーはコンソール・ログ・CSV・JSON・ソース・エラーにも出さない
- 写し（`.cache/`）は git 管理外。**比較の基準は `snapshots/` の CSV**
