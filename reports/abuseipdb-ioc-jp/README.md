# ABUSEIPDB_IOC_JP

脅威情報の索引が持っている送信元 IP のうち、**日本のレポーターが脆弱性攻撃として
報告したもの**。防御目的の受動調査のみ。

```sh
node build.mjs      # 写しを読んで CSV と summary.json を出す。**API は呼ばない**
node report.mjs     # CSV から日本語レポートを組む
node validate.mjs   # 成果物を読み直して検査する（33 項目）
```

## GLOBAL_JP_VULN との違い

| | GLOBAL_JP_VULN | これ |
| --- | --- | --- |
| 母集団 | AbuseIPDB の Blacklist 10 万件 | 索引が持っている IP の写し 860 件 |
| 索引の文脈 | 無い | **アクター名・役割・マルウェア・出典記事・共有証明書が付く** |
| 取得 | この場で API を呼ぶ | **写しを読むだけ。API 呼び出し 0 回** |
| 採用 | 2,763 件 | 31 件 |

判定規則（カテゴリの分け方・コメントの無害化・証拠の段階 E0〜E3・研究スキャナの
見分け方・優先度 P1/P2/P3・点数）は `../global-jp-vuln/rules.mjs` を**共有**している。
**判定を 2 箇所に持たない。** CSV の前 59 列も同一・同順で、索引の文脈 10 列を
後ろに足してある（`validate.mjs` が毎回それを確かめる）。

## 窓

索引側の写しは 365 日ぶんで取っている。GLOBAL_JP_VULN と並べるため、
**写しの報告 1 件ずつの日時で 90 日に絞り直している**（`digest` の `since`）。

- 365 日窓で日本からの報告があるのは **139 件**（`data/ioc/reports/jp-reporters.md`）
- 90 日窓では **55 件**

差は消えたのではなく、報告が 90 日より古いだけ。どちらが正しいということはない。

`abuse_confidence_score` だけは AbuseIPDB 自身が出す値で窓を切れないため
**365 日ぶんのまま**で、この列だけ他の `_90d` 列と意味が違う。

窓の終わりは**写しの取得時刻のうち最新のもの**。`new Date()` を使うと同じ写しから
違うものが出てしまう（2 回走らせて同一になることを確認してある）。

## この母集団の性質 — Tor 出口が 26%

採用 31 件のうち **8 件が Tor 出口**。索引は脅威情報の記事から IOC を集めており、
**記事が Tor 出口を攻撃元として挙げることが多い**ため、ここに溜まる。

Tor 出口は誰でも通れるので、そこに付いたアクター名は**その出口を借りた誰かの話**で
あって、出口の持ち主の話ではない。帰属の根拠には使えない。レポートの第 0 節に
一覧を置いてある。

## 残していないもの

- `reporterId` は distinct を数えるためだけに使い、**値は保存しない**
- コメント原文は保存せず、無害化して短く切ったものと SHA-256 だけ残す
- API キーはコンソール・ログ・CSV・JSON・ソース・エラーにも出さない（この調査は
  そもそも API を呼ばない）
- 対象 IP への接続・走査は行っていない
