# JP_ATTACK_SOURCES

AbuseIPDB をもとに、**日本のレポーターが攻撃として報告した送信元 IP** を集める。
**標準の窓は 30 日**（90 日は文脈として併記）。

```sh
# 取得。GLOBAL_JP_VULN 側が担う
ABUSEIPDB_API_KEY=k node ../global-jp-vuln/build.mjs --new-only   # 母集団を広げる
ABUSEIPDB_API_KEY=k node refetch.mjs --limit 400                  # 30 日の件数を埋める

node build.mjs      # 写しから CSV と summary.json。**API は呼ばない**
node report.mjs     # CSV から日本語レポート
node validate.mjs   # 成果物を読み直して検査（72 項目）
```

## 窓は 30 日。90 日は緩すぎた

索引側の生の写しでの実測では、日本からの報告がある IP は
**365 日 139 件 → 90 日 55 件 → 30 日 31 件 → 7 日 8 件**。
`176.65.139.31` は 90 日で 46 件あるが **30 日では 0 件**で、90 日で数えると
「もう止まっている送信元」が現役として並ぶ。

### 「30 日以内に N 件以上」（実測、分母 356 件）

| 条件 | IP 数 | 観測者で見た場合 |
| --- | --- | --- |
| 1 件以上 | 356 | 1 人以上: 356 |
| 2 件以上 | 307 | 2 人以上: 261 |
| 3 件以上 | 207 | 3 人以上: 208 |
| 5 件以上 | 156 | 5 人以上: 137 |
| 10 件以上 | 109 | 10 人以上: 51 |

### 言い切れる行と言い切れない行を分ける

`jp_report_count_30d` は畳み方を直したあとに足した項目で、**生の報告配列を
残していない**ため手元の写しからは計算できない。引き直すしかない。
写しに世代が混ざるので列 `jp_30d_method` で区別する。

| 区分 | 件数 | 何が言えるか |
| --- | --- | --- |
| `counted` | 356 | **「30 日以内に攻撃報告が N 件」を正確に言える** |
| `latest_only` | 3,628 | 「30 日以内に日本から報告が 1 件以上」まで。**攻撃だったかは不明** |
| 窓内だが攻撃でない | 9 | 引き直したら 30 日以内の報告は走査・スパムだけだった |
| 窓の外 | 405 | 90 日には攻撃報告があるが 30 日以内に日本からの報告が無い |

`validate.mjs` が「確定 + 待ち + 窓内だが攻撃でない + 窓の外 = 主対象」を毎回
確かめる。**この区分の漏れは検査が見つけた**（9 件がどこにも入っていなかった）。

1 回の `/check` で 90 日ぶんが返り、報告 1 件ずつに `reportedAt` が付いているので
**同じ 1 回から 7 日・30 日・90 日の数が全部出る**。API 呼び出しは増えない。

## 「日本からの報告がある」は絞り込みにならない

写しのある 9,763 IP のうち **8,077 件（83%、90 日窓）**に日本からの報告がある。
**窓のせいだけではない。**母集団そのものが絞られている。

```js
eligible = Blacklist 上位 10 万件のうち  score >= 75  かつ
           lastReportedAt が 30 日以内（= 誰かが現に通報している）
```

構造上ほぼ全部が現役の騒がしい送信元で、そういう先は日本のセンサーにも
引っかかる。30 日に絞っても 72% 程度しか減らない。

## 日本の観測者数は「狙われ度」ではない

観測者数は **45 人で天井**になり、分布はそこへ滑らかに向かう（45人:2 / 44人:3 /
43人:9 / 42人:10 / 41人:12 / 40人:30 …）。この数が測っているのは
**「日本にある AbuseIPDB のセンサーのうち何台が見たか」**である。

45 人 = 日本のほぼ全センサーが見た = **インターネット全域を騒がしく走査している先**
であり、標的型の逆。実際、観測者数の上位は証拠段階が全件 E0 だった。

**なので観測者数の降順で並べてはいけない。** 証拠の具体性を先に見る。

## 研究スキャナが 11% 混ざる

攻撃段に当たった 4,967 件のうち **568 件**が Stretchoid(161)・Shadowserver(139)・
Censys(116)・BinaryEdge(45)・Driftnet(44)・LeakIX(33)・Shodan(24) など。
インターネット全域を計測している正規のプロジェクトで、日本のセンサーが「攻撃」と
通報するのは自然だが、攻撃元の一覧に混ぜると母集団が汚れる。

**消さずに別の CSV に出す**（`jp_attack_sources_excluded_scanners.csv`）。
判定は hostname・domain・ISP の**名乗り**で行い、クラウドの AS に属するという
だけでは判定しない。

## 「攻撃」をどこで切るか

カテゴリの集合は `../global-jp-vuln/rules.mjs` の `ATTACK_CATEGORIES` が正。
段への分け方は `tiers.mjs`。**両者が一致することを validate が毎回突き合わせる。**

| 段 | 意味 | カテゴリ | 攻撃に数えるか |
| --- | --- | --- | --- |
| A1 | 侵入・脆弱性 | 15,16,20,21,23 | **はい** |
| A2 | 認証突破 | 5,18,22 | **はい** |
| A3 | サービス妨害 | 4,6 | **はい** |
| A4 | 詐欺・なりすまし | 3,7,8,17 | **はい** |
| A5 | 偵察のみ | 14 | いいえ |
| B | スパム・ボット | 10,11,12,19 | いいえ |
| C | 属性・その他 | 1,2,9,13 | いいえ |

**VPN を使っていることは攻撃ではない。** まとめて「通報あり」と数えると VPN
利用者が攻撃元の一覧に入る。validate が 23 カテゴリ全部が段に入っていることを
確かめる（抜けると黙って数え落とす）。

**1 つの報告に複数のカテゴリが付く**ので、段ごとの数は「カテゴリの付与回数」で
報告件数ではない。

## 畳み方を 2 回直した話

1. `jp_vuln_category_ids`（脆弱性カテゴリ）しか残しておらず、**DDoS(4)・
   フィッシング(7)・詐称(17)・詐欺(3,8)・スパム(10-12)・不正ボット(19) が
   畳んだ時点で消えていた** → `jp_all_categories` を追加
2. 90 日の件数と最新 1 件の日時しか無く、**「30 日以内に 2 件以上」が計算
   できなかった** → `jp_report_count_30d` などを追加

どちらも「この項目が無い行は**まだ数えていない**」という意味で、
「該当なし」ではない。分母を世代ごとに分けてある。

## --resume はバックログを前進させない

既定の選び方は `lastReportedAt` の新しい順で、`cached` は 24 時間以内の写しし
か持たない。1 日経つと全部「未取得」に戻り、**毎回ほぼ同じ IP を選び直す**。
実測で写しが 16,571 行あるのに固有 IP が 9,499 件しかなく、未確認の候補
89,840 件は古い報告しか持たないため一度も選ばれていなかった。

母集団を広げる日は `--new-only` を使う（一度でも引いた IP を候補から外す）。

## 残していないもの

- `reporterId` は distinct を数えるためだけに使い、値は保存しない
- コメント原文は保存せず、無害化して短く切ったものと SHA-256 だけ残す
- API キーはコンソール・ログ・CSV・JSON・ソース・エラーにも出さない
- 対象 IP への接続・走査は行っていない
