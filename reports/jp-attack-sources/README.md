# JP_ATTACK_SOURCES

AbuseIPDB をもとに、**日本のレポーターが攻撃として報告した送信元 IP** を集める。
GLOBAL_JP_VULN より広い切り口（脆弱性だけに限らない）。

```sh
# 取得は GLOBAL_JP_VULN 側が担う
ABUSEIPDB_API_KEY=k node ../global-jp-vuln/build.mjs --new-only   # 母集団を広げる日
ABUSEIPDB_API_KEY=k node ../global-jp-vuln/build.mjs --resume     # 既存を引き直す日

node build.mjs      # 写しから CSV と summary.json。**API は呼ばない**
node report.mjs     # CSV から日本語レポート
node validate.mjs   # 成果物を読み直して検査（51 項目）
```

## この調査で分かった、いちばん大事なこと

### 「日本からの報告がある」は絞り込みにならない

写しのある 9,763 IP のうち **8,077 件（83%）**に日本からの報告がある。母集団が
AbuseIPDB の Blacklist（世界で最も多く通報されている上位）なので、通報者が
何百人も付いている IP には**まず日本の人も混ざる**。

### 日本の観測者数は「狙われ度」ではない

観測者数は **45 人で天井**になり、分布はそこへ滑らかに向かう（45人:2 / 44人:3 /
43人:9 / 42人:10 / 41人:12 / 40人:30 …）。この数が測っているのは
**「日本にある AbuseIPDB のセンサーのうち何台が見たか」**である。

45 人 = 日本のほぼ全センサーが見た = **インターネット全域を騒がしく走査している先**
であり、標的型の逆。実際、観測者数の上位は証拠段階が全件 E0 だった。

**なので観測者数の降順で並べてはいけない。** 証拠の具体性を先に見る。

### 研究スキャナが 11% 混ざる

攻撃段に当たった 4,967 件のうち **568 件**が Stretchoid(161)・Shadowserver(139)・
Censys(116)・BinaryEdge(45)・Driftnet(44)・LeakIX(33)・Shodan(24) など。
インターネット全域を計測している正規のプロジェクトで、日本のセンサーが「攻撃」と
通報するのは自然だが、攻撃元の一覧に混ぜると母集団が汚れる。

**消さずに別の CSV に出す**（`jp_attack_sources_excluded_scanners.csv`）。
判定は hostname・domain・ISP の**名乗り**で行い、クラウドの AS に属するという
だけでは判定しない。

## 「攻撃」をどこで切るか — tiers.mjs の一箇所だけ

AbuseIPDB の 23 カテゴリは「攻撃」から「属性」まで混ざっている。
**VPN を使っていることは攻撃ではない。** オープンプロキシも、走査しただけも違う。
まとめて「通報あり」と数えると、VPN を使っているだけの IP が攻撃元の一覧に入る。

| 段 | 意味 | カテゴリ | 攻撃に数えるか |
| --- | --- | --- | --- |
| A1 | 侵入・脆弱性 | 15,16,20,21,23 | **はい** |
| A2 | 認証突破 | 5,18,22 | **はい** |
| A3 | サービス妨害 | 4,6 | **はい** |
| A4 | 詐欺・なりすまし | 3,7,8,17 | **はい** |
| A5 | 偵察のみ | 14 | いいえ |
| B | スパム・ボット | 10,11,12,19 | いいえ |
| C | 属性・その他 | 1,2,9,13 | いいえ |

`validate.mjs` が 23 カテゴリ全部がどこかの段に入っていることを毎回確かめる
（抜けると黙って数え落とす）。

**1 つの報告に複数のカテゴリが付く**ので、段ごとの数は「カテゴリの付与回数」で
報告件数ではない。

## 畳み方を直した話

`rules.mjs` の `digest` は `jp_vuln_category_ids`（脆弱性カテゴリ）しか残して
おらず、**DDoS(4)・フィッシング(7)・詐称(17)・詐欺(3,8)・スパム(10-12)・
不正ボット(19) が畳んだ時点で消えていた**。生の `reports` 配列も残していないので、
引き直さないと答えられない状態だった。

`jp_all_categories`（`番号:件数;…`）と `jp_all_categories_measured` を足して引き
直した。この項目が無い行は**まだ数えていない**という意味で「該当なし」ではないので、
分母を 2 段に分けている。

## --resume はバックログを前進させない

既定の選び方は `lastReportedAt` の新しい順で上位 `RECENT_CORE` 件。`cached` は
24 時間以内の写ししか持たないので、1 日経つと全部「未取得」に戻り、**毎回ほぼ
同じ IP を選び直す**。実測で写しが 16,571 行あるのに固有 IP が 9,499 件しかなく、
未確認の候補 89,840 件は古い報告しか持たないため一度も選ばれていなかった。

母集団を広げる日は `--new-only` を使う（一度でも引いた IP を候補から外す）。

## 残していないもの

- `reporterId` は distinct を数えるためだけに使い、値は保存しない
- コメント原文は保存せず、無害化して短く切ったものと SHA-256 だけ残す
- API キーはコンソール・ログ・CSV・JSON・ソース・エラーにも出さない
- 対象 IP への接続・走査は行っていない
