# 監視クラスタ（名指しした IP を毎日追う）

```sh
ABUSEIPDB_API_KEY=k node tools/ioc/fetch-watch.mjs   # **ここだけが外に出る**
node tools/ioc/track-watch.mjs      # 観測から state と events を作り直す
node tools/ioc/watch-report.mjs     # 日本語レポート
node tools/ioc/validate-watch.mjs   # 成果物を読み直して検査

# 日次ルーチンに組み込み済み（tools/ioc/daily.sh）。watchlist.json があれば走る
```

対象を増やすときは **`watchlist.json` を編集するだけ**。クラスタの中を `groups` で
分け、各 group に `roles` と IP（`ranges` + `host_range`、または `explicit`）を書く。

## クラスタと役割は宣言。観測には書かない

**`cluster` と `roles` は `watchlist.json` 側の宣言で、API から測った事実ではない。**
観測に書き込むと、**宣言を訂正した途端に過去の観測が嘘になる。**

2026-11-06 に実際そうなった。元は ARTEX と sub2api を**別のクラスタ**として
扱っていたが、利用者の指摘で `38.11.173/221` 側にも sub2api があり、
**全 255 IP に同じリチャージ URL (`198.200.59.85`) がセットされている 1 つの
クラスタ**だと分かった。観測に `cluster` を書き込んでいたので、積んだ観測を
書き換える必要が生じた。

**観測は測ったものだけを持ち、クラスタと役割は突き合わせ時に結合する。**
そうすれば宣言の訂正で履歴を触らずに済む。validate が
「観測に `cluster` / `roles` が入っていない」ことを毎回確かめる。

| 役割 | 対象 | 利用者の観測 |
| --- | --- | --- |
| `sub2api` `artex` | `38.11.173.0/25` と `38.11.221.0/25` の `.1`〜`.125`（250 IP） | ARTEX も起動している |
| `sub2api` `recharge_host` | `198.200.59.85`（1 IP） | リチャージ URL のホスト自身 |
| `sub2api` | `198.200.59.86`〜`.89`（4 IP） | ARTEX は観測されていない |

**母数が小さい役割の割合は読まないこと。** `recharge_host` は 1 IP なので
「通報あり 100%」は「1 件中 1 件」という意味しかない。レポートは
10 IP 未満の役割に「母数不足」と出す。

## なぜ索引（`iocs.jsonl`）に足さないのか

`iocs.jsonl` は 4 つの外部索引から **毎日 `collect.mjs` で再生成される**ので、
手で足した行は翌日消える。

`fetch-abuseipdb.mjs` のほうは **各 IP を一度だけ**引く設計で、`abuseipdb.jsonl` に
判定がある IP は `alreadyKnown` で二度と引かない。枠を無駄にしないための正しい設計
だが、**毎日追う用途とは真逆**。接ぎ木すると本線の枠配分が壊れる。だから別立てにする。

## 枠の配分（`/check` は 1 日 10,000 回・UTC 0 時リセット）

| | 件数 |
| --- | --- |
| 本線のエンリッチ（索引ぶん） | 約 100 |
| **この監視** | **255**（既定の上限 400） |
| 日本向け攻撃元の収集 | 9,000 |
| 予備 | 645 ほど |

**監視は本線の後、9,000 件の掃き出しより先**に回す。件数が小さく、
「初めてフィード以外の通報が付いた日」を逃さないことの価値が高い。

## 状態は観測から毎回作り直す

```
observations/<日付>.jsonl   ← **これだけが真実**。1 日 1 ファイルで積み上がる
state.jsonl                 ← 観測から再生。1 IP 1 行の現況
events.jsonl                ← 観測から再生。変化だけ
shapes.jsonl                ← 観測から再生。本文の形ごとの広がり
```

前回の `state` を読んで更新する作りにすると、**一度おかしくなった状態が永久に残る**。
`track-domains.mjs` と同じ規則にしてある。

写し（`data/ioc/.cache/watch-abuseipdb/`）は git 管理外で容器も使い捨てなので、
**観測ファイルが残らないと翌日には前日が無い**。`daily.sh` の `git add` に
`$WATCH` を入れてある（日本向け収集の台帳を入れ忘れて 7 日ルールが効いていなかった
のと同じ失敗を繰り返さないため）。

## いちばん重い変化は `first_independent_report`

その IP に**初めてフィードの一括登録以外の通報が付いた日**。
`artex` の 8 IP で 2026-10-31 にこれが起き、気付くまで 6 日かかった。
この仕組みはそこを翌日に出すためにある。

| 変化 | 意味 |
| --- | --- |
| `first_independent_report` | **初めてフィード以外の通報が付いた**（いちばん重い） |
| `first_report` | 初めて通報が付いた |
| `already_*_at_first_sight` | 監視を始めた時点で既にそうだった（その日に起きたのではない） |
| `reporters_up` | 通報者の数が増えた |
| `new_category` | これまで無かったカテゴリが付いた |
| `jp_report_up` | **日本からの通報が増えた** |
| `score_up` | スコアが上がった |
| `backdated_report` | 過去の日付の通報が後から増えた（さかのぼり投稿） |
| `resubmitted` | 観測は増えていないが投稿時刻だけ進んだ |

### 何を変化と呼ばないか

1. **スコアの減衰。** 通報が増えなくても時間で下がる（実測で `198.200.59.85` が
   18 → 16、通報は 3 件のまま）。**下がりは出さない。**
2. **投稿時刻だけが動いた日。** `resubmitted` として別に出すが、攻撃の観測ではない。
3. **引けなかった日。** 観測に入れない。**「通報なし」ではなく「分からない」。**
4. **1 つの事実に 3 行。** 初通報の日は `reporters_up` と `new_category` が必ず
   同時に立つので、`first_report` だけを出す。雑音で本当の変化が埋もれないように。

## `reportedAt` は観測日、`lastReportedAt` は投稿日

2026-11-06 に実測した（`reports/artex-timeline/README.md` に詳細）。

- フィード本文の `Last observed <日付>` が `reportedAt` と **58/58 件一致**
- `lastReportedAt` は 57/65 件でそれより後ろ、前になった例は 0 件
- さかのぼり中央 **1.04 日**・最大 **7.32 日**

**`lastReportedAt` を活動日として読んではいけない。** また **過去の日付の集計は
確定しない**（後日引き直すと増える）。`backdated_report` がそれを毎日可視化する。

## フィードの一括登録を件数だけで決めない

同じ形が多数の IP に付いていれば一括登録の印だが、**それだけでは取り違える**。
被害者側の通報は **8 IP** で、閾値 10 を**ぎりぎり下回っただけ**だった。
もう 2 IP 分あれば一括登録として割り引いていた。

そこで実測した判別子を併せて見る。

| | さかのぼり最大 | 対象（255 IP の） | カテゴリ |
| --- | --- | --- | --- |
| フィード（BR） | **7.32 日** | 22.7% | Exploited Host（20） |
| 被害者側（IN） | **0.00 日** | 3.1% | Web App Attack（21） |

**ずれが 0 なら、IP の数が閾値を超えても一括登録とは呼ばない。**
人が確認した形は `watchlist.json` の `feed_shapes` に書ける。
**どちらも印であって判定ではない。** 該当しても行は捨てない。

### さかのぼりを形に帰属させられる条件

**その形がその IP の唯一の通報のときだけ。** `lastReportedAt` は IP ごとに 1 つ
しかないので、通報が 2 件ある IP ではどちらの投稿時刻か決まらない。
最初の版は IP 単位で持った値をその IP の全部の形に配っていて、
`38.11.173.107` のフィードぶん（3.06 日）が被害者側の形に移り、
**ずれ 0 を 3.06 日に見せていた**。validate が数え直して確かめる。

## 差し込む記号に山括弧を使わない

`rules.mjs` の `sanitize` は `<[^>]{0,200}>` を HTML タグとして**消す**。
`<date>` を差し込むと、**もう一度無害化を通った時点で placeholder ごと消える**。

```
"... Last observed <date> UTC."  →  "... Last observed UTC."
```

畳んだ形は表示や再集計で何度も通るので、角括弧 `[date]` にしてある。
`sanitize` 自身が入れる `<email>` と `<internal-host>` も `shapeOf` の出口で
畳み直すので、`shapeOf(shapeOf(s)) === shapeOf(s)` が成り立つ（validate が確かめる）。

## 残していないもの

- **`reporterId` は保存しない。** 「同じ通報者か」は IP ごとの通報者数の増減で足りる。
  識別子に塩を付けて畳んでも `reporterId` は小さな整数なので総当たりで戻せる。
  塩を git の外に置くと別の容器で観測が再現できない。**そもそも持たない。**
- **通報コメントの原文は保存しない。** 日付と数字を畳んだ「形」だけ。
- API キーはコンソール・ログ・観測・ソース・エラーにも出さない。
- 写し（`data/ioc/.cache/watch-abuseipdb/`）は git 管理外。

## 2026-10-30 の観測は復元したもの

監視を作る前の日なので、`reports/artex-timeline/snapshots/2026-10-30_*.csv` から
復元して置いた。**行に `source: "reconstructed_from_snapshot"` の印が付いている。**
本文は当時の無害化済み抜粋（120 字）由来なので、形の畳み方が取得ぶんと厳密には
一致しない。validate が「同じ日の中で復元と取得が混ざっていない」ことを確かめる。

これがあるおかげで、監視の初日から 10-31 の `first_independent_report` が出る。
（復元した行にも `cluster` は入っていない。宣言は結合するため、1 クラスタへの
訂正でこのファイルを書き換える必要はなかった。）
無ければ全部 `already_*_at_first_sight` になり、初日は何も分からなかった。
